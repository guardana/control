How it works

Set the rules. Review the run.

You write the rules once. Control applies them to every call, and helps you check the whole task afterwards.

01 · Decide

Rules in front of every call

A signed policy allows, blocks or holds each tool call before it runs. In a mode that enforces, a call that cannot be decided does not go through.

What you get

Answers you can show someone.

Not a promise that an agent will behave. A record of what it asked, what your rules said, and what nobody saw. The status page labels each one.

Why was that call allowed?

experimental

Each decision is recorded before the call runs, unless you let reads run unrecorded. A record holds who asked, what for, the verdict and the policy version that made it.

What did we not see?

experimental

A coverage map shows which paths were decided, which were only watched, and which nobody observed. Unknown is never shown as safe.

Can we stop it?

experimental

Pause a tool, a server or an agent. Stop one run after a confirmed finding. Operations already running are not cancelled.

Can our auth service overrule it?

experimental

Connect the authorization service you already run, over AuthZEN. It can refuse a call. It can never widen what your policy allows.

What about tools that are not MCP?

experimental

Tools of your own ask Control before they act, over a small API with a Python client, or through a coding agent's hooks. Your client enforces the answer.

Does it fit what we already watch?

experimental

Records leave over OpenTelemetry. Runtime traces and an outbound proxy's log come in as observations beside the decisions.

Signed operations

Signed, from the rule to the release.

In Control, authority comes from a signature you can check. Each link below names what is signed and what it is today.

  1. The rules

    A policy is a bundle signed with your key. The gateway takes no unsigned policy.

    implemented
  2. That the rules are current

    A second key vouches that the bundle is still the newest. A stale policy stops deciding.

    experimental
  3. Who may operate

    Operators are named in a roster signed by a root key you pin.

    experimental
  4. What operators do

    In signed mode an approval, a pause, an opened run or a stop counts only with an operator's signature.

    experimental
  5. What you download

    Releases are built from a tag, signed and attested. You can verify an archive before you run it.

    experimental
  6. The record itself

    Records linked by hashes, with signed checkpoints, so a removed or altered record shows.

    planned · B29

Quickstart

Start locally. Then connect your tools.

The demo needs no Go and no model key. Download the demo archive from the release, extract it, and run one command.

# a gateway, two risky demo servers and an approval page
$ bin/guardana-gateway dev --decision-point=silent \
    --config examples/vulnerable-mcp-agent/demo.yaml \
    --policy examples/vulnerable-mcp-agent/policy.json

# then make three calls: one runs, one is blocked, one waits for you
# point your agent at the gateway instead of the server
$ guardana-gateway run --config <file>

# start from a tested policy: reads run, writes wait
# test your policy against cases, then sign it
$ guardana-control policy test <dir>
$ guardana-control policy sign --key <file> \
    --out <file> <document>
# compare a recorded run with its procedure
$ guardana-control supervise --procedure <file> \
    --runs <dir> --run <run-id> --findings <dir>

Where it stops

Connected paths. Visible limits.

Control only knows what is connected to it. This is an alpha: do not deploy it as a security boundary.

Decided before it runs

MCP calls that go through the gateway.

It cannot see a call that goes around it.
Decided, you enforce

Your own tools asking through the API.

It cannot prove the client obeyed.
Watched afterwards

Runtime traces and an outbound proxy's log.

A report, not proof of every action.
Unknown

Anything nobody connected or logged.

Shown as unknown, never as safe.

Questions

Before you connect it

Something else? Open an issue and tell us what you are trying to control.

Does a model decide anything?

No. Decisions come from structured rules. A model may suggest or summarise. It never grants permission.

Does it stop prompt injection?

It does not detect it. It limits what an injected agent can do: each action is still decided by your rules, and the risky ones wait for a person.

Does supervision run on its own?

Not yet. You start a check on a recorded run today. Continuous supervision is planned (B28).

What does it store, and where?

The action, the decision, the policy version and a hash of the answer, on your machines. Capturing prompt or tool content is off by default. There is no hosted service.
